# Agent 执行纪律（元层面）

## 为什么需要这个 skill

一次数模论文协作里，最贵的错误全都不是"不会做"，而是这四类：

1. **Skill 写了却没读**：09-04 已落盘 4 个 skill，后续会话仍把同一个坑踩了三次（含斜杠分支名 ref 静默失败）。
2. **断言而不实跑**：说"CI 应该转绿"，用户要求补跑才确认。
3. **为省一步引入复杂手工流程**：用 `read-tree`/`commit-tree` 手工造提交，结果索引未清理，上一分支文件以 staged 残留污染新分支。
4. **对环境能力误判**：白天判断"沙箱可非交互 push"，当晚被证伪。

共同点：**动作做了，但没有被验证，也没有被复查。**

## 根因三分法（出错后先归类，再修）

| 类型 | 含义 | 典型表现 | 对策 |
|---|---|---|---|
| **忽视** Ignored | 已知信息没用上 | skill/契约写了却没读；没读 `start-<角色>.md` 就动笔 | 开工前强制检索并逐条打勾 |
| **遗漏** Omitted | 流程缺一步 | 开工没 fetch；切分支没 `reset --hard` | 固化成 checklist 的固定步骤 |
| **误判** Misjudged | 对环境/结果判断错 | 以为沙箱能 push；以为 CI 用两点 diff | 每一步产出都要有可观测证据 |

分类的意义：忽视 → 补检索动作；遗漏 → 补流程步骤；误判 → 补验证证据。三者修法不同，混着修会反复复发。

## 开工五问（动手前先答完）

1. **基线新鲜吗？** `git fetch` 后 `git log --oneline -1 origin/main`，确认本地不是旧基线。
   *陈旧基线推上去 = 删除队友产出。这是本次最严重事故的根因。*
2. **有现成 skill / 契约吗？** 列出相关 skill 名，读一遍，逐条对照当前任务。
3. **有现成脚本可复用吗？** 先 `ls scripts/`、`grep` 关键字，再决定要不要自己写。
4. **这一步的验收证据是什么？** 先写下来，做完拿证据对账。
5. **最简路径是什么？** 能用一条常规命令搞定的，不要手工构造。

## 验证优先（禁止断言）

- ❌ "应该转绿"、"应该没问题"、"理论上可以"、"大概率是"
- ✅ 用**同一脚本同一参数**跑一遍，贴 exit code 与关键输出

环境能力（能否 push / fetch / 联网 / 读到某个文件）必须**每次实测**，不能凭上一次经验推断——网络、凭证、代理状态都会变。本次就出现过"昨天能 fetch，今天 Connection reset"。

## 简化优先：复杂手工流程是 bug 温床

选型顺序（从上往下，能停就停）：

1. **常规命令**：`rebase` / `merge` / `checkout` / 脚本
2. **常规命令 + 已验证的绕行**：如仓库含斜杠分支名，必须 Python 直写 ref（见 `sandbox-git-gh-pitfalls` §1）
3. **手工构造**：`read-tree` / `write-tree` / `commit-tree` ← 只在 1、2 都确认失效时用

跳到 3 之前，必须在 skill 里确认 1、2 确实失败，不能因为"看起来优雅"或"省一步"就手工构造。

**已付过的学费**：手工 `commit-tree` 造提交 → 索引未清理 → 上一分支文件以 staged 残留污染新分支。
**凡是绕开 git 正常路径的手法，收尾必须** `git status` **逐项确认无残留。**

## 一次是意外，两次是流程缺陷

同一现象第二次出现，立刻停下做两件事：

1. 把「现象 + 根因 + 修法」写进**对应 skill**——不是写进会话日志。日志会沉底，skill 会被检索。
2. 在 skill 里加一条**动作前自检**，而不只是事后修法。只写修法不写自检，第三次还会踩。

已确认的重复坑：

| 坑 | 次数 | 状态 |
|---|---|---|
| 含斜杠分支名 ref 静默失败 | 3 | 已固化绕行手法 |
| `premerge_check.py` 依赖进程 cwd 误报 | 2 | 已固化 cwd=REPO |
| 本地基线陈旧未 fetch | 2 | 已固化为开工五问第 1 条 |
| 沙箱能力误判（push/fetch/联网） | 2 | 已固化为"每次实测" |

## Skill 的正确用法

**Skill 写了 ≠ 生效。** 典型失效模式是"写下来就当完成了，动作前不去检索"。

- **动作前**：主动检索相关 skill，不要等用户提醒
- **执行中**：逐条对照，不是扫一眼
- **踩新坑时**：当场更新 skill，不留到"待会儿统一整理"——那时上下文已经丢了

## 分层交付与止损（交付期纪律）★ 2026-09-14 补

来源：一次数模大赛收尾复盘。**算得对，但没落盘。**

### 1. 交付分层，前一层闭环才进下一层

| 层 | 内容 | 未闭环的代价 |
|---|---|---|
| **生存线** | 官方硬性项：页数/页边距、附录完整源码、支撑材料文件列表、禁身份、文件命名、**在线地址可访问（仓库不能还是 private）** | 直接出局 / 取消评奖 |
| **评分线** | 影响得分的实质：结论章口径、摘要结构、标题、跨文件数字一致性 | 扣分 |
| **锦上添花** | 格式美观：小数位统一、字体、表格线、图题精简 | 观感 |

**真实失误**：生存线还没闭环（Word 侧替换未执行、仓库仍是 private）时，我跳去做锦上添花（表 4-7 小数位），把交稿前夜花在了低权重项上。
**动作前自检**：动手前先问一句「**上一层闭环了吗？**」——没闭环就先回去。

### 2. 交付形态必须匹配用户的执行预算

- 用户每天只有 <1h。**产出 5 份"待手动粘贴的文字建议" = 把工作量原样转嫁回去**，等于没交付。
- **正确形态**：能直接落盘的落盘（改好的备件文件 / 打好的包 / 已执行的替换）；确实只能手动的，**合并成一份清单一次给全**，不要零散追加。
- **判据**：产出物若还需要用户"再操作 N 步才生效"，它就不是完成品，只是半成品。

### 3. 同类工具调用 > 3 次即停（防死循环）

- 同一动作（读同一文件、转同一格式、跑同一命令）**无进展超过 3 次 → 立即停止并报告**。
- **真实失误**：导 PDF 时反复读取同一个记忆文件 40+ 次，既没换路径也没报告，直接导致该任务未完成、还烧掉整轮。
- **止损动作**：换路径（换工具 / 换命令 / 换输入形态）→ 仍不行则**明确报告故障 + 给出手动方案**，把决定权交回用户。
- **与"重试"的区别**：网络类失败值得重试几次（见 `sandbox-git-gh-pitfalls` 坑 4）；**语义类失败**（读同一文件、跑同一转换、改同一断言）重试无意义。

### 4. 定级前必查文件，不凭印象

- 对任何"要不要改"的判断，**先打开文件核实**再定级。
- **真实失误**：`+84%` 这条第一次凭印象判"必改"，第二次查文件后改"都行"，第三次查到 json 里存在同数字反方向的"下降 84%"才重新定为"必改"。三次移动由证据驱动，但**第一次凭印象就是错的**。
- **方向自我校准法**：把本轮所有定级变动列出来看方向——全朝一个方向（都收紧/都放宽）要警惕迎合；方向不一致且每次由新证据驱动，说明判断源是文件。**诚实写出"哪条上调过、哪条下调过"**（用户明确要不找借口的失误承认）。

### 5. 备件 ≠ 落盘

生成备件（改好的 docx、打好的 zip、写好的补丁）只是中间物。**回读目标位置确认生效**才算闭环，否则以"清单已给/备件已生成"结案 = 未交付。详见 `docx-final-surgery` §G5。

## 禁忌

- 不要在没 `git fetch` 的情况下判断基线新旧
- 不要在没实跑的情况下报告"通过"
- 不要为省一步引入手工构造流程
- 不要把第二次修复只写进会话日志
- 不要在同一坑上重试超过两次——第二次就该停下来写规则
